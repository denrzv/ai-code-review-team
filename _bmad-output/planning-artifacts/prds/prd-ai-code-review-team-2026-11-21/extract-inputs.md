## 1. Problem / mission / why this exists

- Mission: review a fixed Git diff with specialist Correctness, Security and Performance agents. An LLM Planner picks the next agent, a Temporal Workflow orchestrates durably, and deterministic Java validates findings before it publishes JSON and Markdown reports. [README]
- Core design rule: "LLMs suggest decisions and evidence; Temporal controls execution; Java validates claims and enforces security boundaries." [README]
- Positioning: a **learning-oriented, educational proof of concept**, not a product or a banking production system. It should favour transparent control and evaluation over scale. [CLAUDE], [A&R A-01], [README "proof of concept"]
- Production readiness is explicitly **not** implied, even when the exit criteria are met. [EVAL Exit criteria]
- Experimental question it exists to answer: does a multi-agent team add value over a single agent? "A team with extra LLM calls is not necessarily better than a single agent." The project must measure this before claiming it. [EVAL], [ADR-007], [ARCH goal 5]
- Secondary learning goal: show durable recovery after a worker crash without rerunning successful Activities, so less work and model spend is wasted. [ARCH goal 4], [ADR-003]
- Current status: architecture and plan only, with no runtime code committed. [README Status]

## 2. Users / operators / stakeholders

- **Reviewer**: starts and queries a review through the REST API. [ARCH C4 context]
- **Developer**: maintains the allowlisted local synthetic repository. [ARCH C4 context]
- **Human reviewer, responsible for acting on findings**: the system makes no automated modifications or PR comments. [A&R A-10], [ADR-006 "Human assessment ... still needed"]
- **Implementers / reviewers / AI coding agents (Claude Code, Codex)**: the stated audience of the architecture doc and the code-generation guidance. [ARCH header], [PLAN Code generation guidance], [README Documentation]
- **Governance / approval authority** (implied): needed before any real bank or private code is sent to DeepSeek. [A&R A-02], [CLAUDE rule 8], [ARCH security]
- **External systems as stakeholders**: DeepSeek Chat Completions API (billed per token, acts as data processor), Temporal Service, and a read-only Git repository. [ARCH C4 context]
- **Evaluation adjudicator** (implied): judges semantic findings against the goldset, either blind or consistently. [EVAL protocol step 5]

## 3. Capabilities (what the system must do)

### 3.1 Review submission and lifecycle
- Accept an asynchronous review request (repositoryId, base commit, head commit, mode SINGLE_AGENT/MULTI_AGENT). Return HTTP 202 with a location. Do not block HTTP while the review runs. [CONTRACTS REST], [ARCH Review API]
- Start a review with a stable reviewId supplied by the caller or generated by the server, with idempotent conflict semantics. [CONTRACTS REST], [ARCH failure table]
- Report status and progress, plus report links. [CONTRACTS REST GET], [CONTRACTS `@QueryMethod progress()`]
- Return the stored report when the review is complete or partial. [CONTRACTS REST]
- Accept cancellation, propagate it within bounds, and never show a misleading COMPLETED for a cancelled review. [CONTRACTS REST cancel], [EVAL CANCEL]
- Lifecycle `SUBMITTED → RUNNING → COMPLETED | PARTIAL | FAILED | CANCELLED`. PARTIAL must expose reasons and coverage and must not read as a clean review. [ARCH Review lifecycle], [PLAN quality bar]
- Validate that a repository ID is on the allowlist. [ARCH Review API]

### 3.2 Pinned, read-only repository access
- Review a pinned comparison of two commits (full SHAs), not a moving working tree. Reject changes that exist only uncommitted. [ARCH goal 1], [A&R A-07], [CONTRACTS]
- Read blobs by commit SHA, and keep reading the original HEAD even if the repository changes. [ARCH security, failure table]
- Read-only agent tools: listChangedFiles, getDiff, readFile (line range), searchCode, listRelatedTests, getBuildMetadata. [CONTRACTS Git read port]
- Every tool is bound to one immutable ReviewSnapshot. [CONTRACTS invariants], [ARCH concurrency]
- Validate HEAD and base existence and the ancestry/compare policy. [CONTRACTS]

### 3.3 Planning and delegation (multi-agent)
- An LLM Planner returns a typed PlanDecision (DELEGATE to a known role, or COMPLETE) with a task, a rationale and a topicKey. [CONTRACTS orchestration], [ADR-003]
- Delegate to Correctness, Security or Performance specialists, choosing dynamically and repeating where useful, within hard limits. [ARCH goal 2], [PLAN M3]
- Validate planner output against an enum allowlist. The planner cannot choose unknown agents, extend budgets or run operations itself. [ARCH Planner Activity], [CONTRACTS], [ADR-010]
- Stop on COMPLETE or when a budget runs out. Budget exhaustion yields PARTIAL with a reason. [ARCH failure table], [EVAL BUDGET_EXCEEDED]
- Pass a bounded summary of earlier work to later planner and agent calls. [ARCH Persistence], [ADR-009]

### 3.4 Specialist review
- Each specialist runs a bounded tool-calling loop over the read-only tools and returns an AgentResult. The result holds FindingCandidates, unresolved questions, a summary of the work done, and usage. [ARCH Agent Activities], [CONTRACTS AgentResult]
- Prompts are role-specific and versioned. [CONTRACTS LangChain4j boundary]
- Single-agent baseline mode: role SINGLE / reviewSingle, using the same model, snapshot, evidence rules and comparable budget. [CONTRACTS], [ADR-007]

### 3.5 Finding validation and evidence
- Deterministically validate each candidate: file exists at HEAD, commit SHA, line range, and that the quoted snippet matches. [ADR-006], [ARCH Evidence Validator]
- Assign one of SOURCE_VERIFIED, NEEDS_REVIEW or INVALID_EVIDENCE. SOURCE_VERIFIED attests location only, not that the bug is real. [CONTRACTS], [CLAUDE rule 6]
- Track rejected and uncertain candidates. Keep unverifiedCandidates separate from rejected ones, and keep the audit trail. [ADR-006], [CONTRACTS JSON note], [ARCH failure table]
- Deduplicate only on normalized issue plus location, keeping provenance. [ARCH Evidence Validator]
- Handle malformed model JSON with rejection or one bounded repair attempt. [EVAL BAD_SCHEMA]

### 3.6 Reporting and artifacts
- Produce a typed JSON report (schemaVersion "1") and a human-readable Markdown report. Both carry source locations, evidence status, coverage, limitations and usage. [ARCH goal 3], [CONTRACTS JSON sample]
- Write `output/reviews/<reviewId>/report.json`, `report.md` and a manifest (hashes, SHAs, model and prompt versions, limitations). Writes are atomic and idempotent, and the path is deterministic. [EVAL Report format], [ADR-009], [ARCH failure table]
- Return a small ReportReference (jsonPath, markdownPath, sha256). [CONTRACTS]

### 3.7 Observability, usage and cost accounting
- Trace IDs: reviewId, workflowId/runId, agentInvocationId, Activity attempts, model/provider, prompt version, tokens and a cost estimate. [ARCH security]
- Record actual provider usage when it is available. Otherwise use estimates that are clearly labelled as such. Record attempt IDs too. [CONTRACTS Pricing], [A&R A-16]
- Persist prompt version, model ID, fixture ID, review parameters and an input digest so runs are reproducible. [ARCH Recovery boundaries]

### 3.8 Durable recovery
- Resume after a worker crash without rerunning completed Activities. An interrupted Activity may retry, and the retry is recorded. [ARCH goal 4], [A&R DoD reliability]
- Replay must reuse a persisted PlanDecision with no extra planner API call. [EVAL PLANNER_REPLAY]

### 3.9 Evaluation harness
- A seeded synthetic Java/Spring fixture with a hidden goldset. Run single-agent and multi-agent modes 3–5 times each and compute the metrics. [EVAL], [PLAN FEATURE-013/014]

## 4. Non-functional constraints

### Security / capability
- Zero Git write capability and zero generic shell execution. No checkout, no file modification, no network tools, and no running project code or tests. [ARCH goal 6], [ADR-005], [CLAUDE rule 4]
- Path policy: allowlisted repos only. Reject `..`, symlink escapes, out-of-policy submodules, and oversized or binary content. [ARCH security], [CONTRACTS tool contract]
- Treat source, comments, diffs and LLM output as untrusted, since they can carry prompt injection. Source-controlled content cannot override tool policy. [README Security], [CLAUDE rule 8], [CONTRACTS]
- Redact secrets in tool output. Never log API keys or source text indiscriminately. Inject keys through environment variables or secrets and never commit them. [CONTRACTS tool contract], [ARCH security], [README Security]
- Policy is enforced in Java and Temporal, not in prompts. [ADR-010], [CLAUDE rule 5]
- PoC auth model is local-only. [ARCH Review API]

### Budgets / limits
- ReviewBudget: maxDelegations, maxInvocationsPerTopic, maxToolCallsPerInvocation, maxEstimatedInputTokens, maxEstimatedOutputTokens, maximumElapsedSeconds. [CONTRACTS]
- readFile returns at most **200 lines** per call. Diffs, results, changed files, output tokens, tool requests and total duration are all bounded. [CONTRACTS], [ARCH security]
- Capability, attempt, token, cost and time limits are enforced in code. [CLAUDE rule 5]
- Retries are bounded and classified. HTTP retries must not stack on top of Temporal retries without limit. [ARCH failure table]

### Durability / determinism
- The Temporal Workflow is the sole durable orchestrator. Workflow code does no LLM, file, HTTP, JGit, random or wall-clock work. [CLAUDE rule 2], [ARCH Workflow engine], [CONTRACTS]
- The durability unit is one Activity per agent invocation. Calls inside an Activity are not durable. [ADR-004]
- Activities run at least once. The system never claims exactly-once billing or exactly-once tool execution. [ARCH], [CONTRACTS Pricing], [CLAUDE Critical caveat]
- Temporal must persist storage for crash tests, not run in ephemeral mode. [README], [ARCH Infra], [ADR-008]
- Event history holds only small DTOs, not source or transcripts. Payload size and history growth are restricted. [ARCH Persistence], [ADR-009]
- Breaking workflow changes need versioning and a replay test. [CONTRACTS Serialization]
- Reports are deterministic. [PLAN QA], [ADR-006]

### Privacy / data handling
- Only synthetic or explicitly approved code may go to DeepSeek, which is treated as an external data processor. [ARCH security], [A&R A-02], [CLAUDE rule 8]
- Logging is minimal, with secret scanning and redacted traces. [A&R risks]
- The goldset is never exposed to agent tools or prompts. [EVAL], [PLAN QA]

### Cost
- Retries can bill twice, so retries are bounded and attempts and cost are logged. AgentUsage may undercount. [CONTRACTS Pricing], [A&R risks]
- Recheck pricing at implementation time, and log model version and usage. [A&R A-16]

### Data persistence
- No application database for lifecycle state (no PostgreSQL, Kafka, Redis). [CLAUDE rule 7], [README], [ADR-008], [A&R A-12]
- Artifacts live on local disk, which is enough for a single worker. [A&R A-11]

## 5. Explicit non-goals / out of scope

- Production deployment, Temporal Cloud topology, multi-tenant SaaS, production scale, unlimited repositories. [CLAUDE Non-goals], [ARCH Non-goals], [A&R Out of scope]
- Remote proprietary repos and confidential repository access. [CLAUDE], [A&R]
- Arbitrary shell execution, CI-executed arbitrary code, running project code or tests (dynamic verification). [CLAUDE], [ARCH], [A&R A-08]
- Repository mutation, fixing code and autonomous repair. [CLAUDE], [ARCH], [A&R]
- Opening or commenting on PRs, automated PR writing. [CLAUDE], [ARCH], [A&R]
- MCP. [CLAUDE], [README]
- RAG / vector DB, long-term agent or semantic memory. [CLAUDE], [ARCH]
- Per-LLM-call Temporal checkpointing (deferred to v2). [CLAUDE], [ADR-004], [README]
- Exactly-once LLM charges. [ARCH]
- Semantic proof that every finding is a real bug. [ARCH], [A&R A-15]
- Access control for untrusted remote users, enterprise audit retention. [A&R]
- External web search, LangGraph. [A&R]
- A nested LangChain4j supervisor as the main scheduler, and AgenticScope persistence. [CLAUDE rule 3], [ADR-003]
- Large-repo indexing and prompt compaction (inputs are fixture-scale). [A&R A-14]
- Deleted-only (BASE-side) evidence citations in v1. [CONTRACTS], [A&R A-09]

## 6. Success criteria / evaluation metrics / acceptance signals

- **Metrics:** recall (gold defects matched by verified findings divided by total), precision (judged on semantic validity, not just SOURCE_VERIFIED), false positives, coverage, latency (overall and per Activity), cost (tokens and USD, with retry uncertainty disclosed), planner quality, durability, safety. [EVAL Metrics]
- **Protocol:** pin one commit pair and the model parameters. Run single-agent **3–5×** and multi-agent **3–5×** with a comparable *total* token or spend budget. Match findings by root cause, location and failure scenario. Report averages, variability, partial and failed runs, and a cost/quality frontier. [EVAL protocol], [PLAN FEATURE-014]
- **Fixture:** `samples/order-processing-service` with **9 seeded defects plus 1 non-defect control**. The goldset lives in `samples/goldset.json`. [EVAL]
- **Durability tests:** WORKER_RESTART, PLANNER_REPLAY, DOUBLE_WRITE, RATE_LIMIT, BAD_SCHEMA, FAKE_LINE, BUDGET_EXCEEDED, CANCEL, PROMPT_INJECTION, each with an expected outcome. [EVAL Durability experiments]
- **Reliability definition of done:** kill the JVM mid-specialist and resume without reruns; record retries of the interrupted Activity; stop with PARTIAL on budget exhaustion; reject a corrupted line reference; deny traversal and symlink escape; rerunning the frozen fixture gives reproducible summary metrics. [A&R DoD]
- **Exit criteria:** all correctness and safety tests pass, crash recovery is demonstrated, and the baseline comparison is published **even if multi-agent underperforms**. [EVAL Exit criteria]
- **PR quality bar:** one FEATURE per PR, unit tests required, LLM end-to-end tests optional or manual, no false "no issues found", before/after usage and time metrics. [PLAN]
- **Milestones M0–M5** serve as acceptance gates (see section 10). [PLAN]

## 7. Implementation / technology decisions (addendum, not PRD body)

- Java 25 LTS, Spring Boot 4.1.x (exact version validated through Maven), Maven. [README], [CLAUDE rule 9], [ARCH Infra]
- Temporal Java SDK with one `CodeReviewWorkflow` per reviewId. Activities: PlanActivities, SpecialistActivities, ReportActivities. Plain SDK is acceptable instead of the Spring integration. [ADR-003], [CONTRACTS], [ADR-open]
- LangChain4j: Planner and specialists as ports/adapters, with `@Tool`/`@P` annotations. No `AgenticServices.supervisorBuilder()`. [CONTRACTS], [ADR-003]
- DeepSeek `deepseek-flash`, non-thinking, through the LangChain4j OpenAI-compatible adapter. Base URL, key and model are configured externally. Alternatives considered: GPT, Ollama/MLX, DeepSeek V4 Pro, direct HTTP. [ADR-002], [README]
- JGit `RepositoryReadPort` rather than the CLI. [ADR-005], [ARCH]
- Single JVM with logical packages (api, application, domain, agents, git/llm/report infra, temporal). API and Worker share a JVM at first. [ADR-001], [ARCH]
- Local Temporal dev server with persistence. [ADR-008]
- Jackson records/DTOs with explicit schema versions. [CONTRACTS]
- Artifacts are stored outside Temporal history in content-addressed files, with object storage as a v2 option behind `ReportStorePort`. [ADR-009], [ARCH]
- Domain and orchestration records and enums as sketched in contracts (ReviewSnapshot, FindingCandidate, ReviewFinding, PlanDecision, AgentTask, AgentResult, AgentUsage, ReviewCommand, ReviewBudget, ReportReference, ReviewRunResult). [CONTRACTS]
- Testing: JUnit; Temporal in-memory test environment plus a local persistent service; mock DeepSeek contract tests; opt-in end-to-end. [EVAL Testing layers], [README]
- Pin versions through a BOM and document the compatibility matrix. [A&R risks]
- Process rules (one FEATURE at a time, ADR for every architectural change) belong to the engineering process, not the PRD. [CLAUDE], [PLAN]

## 8. Open questions, risks, assumptions, validation spikes

### Validation spikes (mandatory before the orchestrator)
- DeepSeek tool calling, non-thinking parameter transport, JSON output, multiple sequential tool calls and error behaviour through the chosen LangChain4j adapter. [ADR-002], [ADR-open], [A&R A-04], [PLAN M1 / FEATURE-002]
- Exact compatible releases of the Temporal SDK, LangChain4j/Agentic, JGit and Surefire on Java 25 and Boot 4.1.x. [ADR-open], [A&R Q1], [CLAUDE rule 9]

### Open questions
- Does DeepSeek Flash reliably handle structured planner JSON and the tool schema? [A&R Q2]
- How should permanent bad-request errors be classified against 429 and transient errors? [A&R Q3]
- Is shell-free JGit blob search adequate? [A&R Q4]
- How should report files be reconciled when the write succeeds but the acknowledgment is lost? [A&R Q5]
- Should a redacted model transcript be kept as an opt-in debug artifact? [A&R Q6]
- Does the seeded set need hard-to-verify cases? [A&R Q7]
- Should snippets be replaced with digests for sensitive projects? [ADR-open]
- How should billing estimates be persisted when a retry makes accounting uncertain? [ADR-open]
- LangChain4j Agentic APIs may be experimental, so the project prefers an explicit planner and the stable Tool APIs. [A&R A-13], [ADR-open]

### Key risks (summary)
- Adapter incompatibility, replay nondeterminism, double billing, runaway delegation, hallucinated findings, prompt injection, context and payload overflow, loss of ephemeral disk, Git GC removing pinned objects, leaked tokens or code in traces, version drift, and a misleading claim of multi-agent superiority. [A&R Key risks]

### Assumptions
- A-01..A-16, for example: an educational PoC, synthetic inputs, a persistent local Temporal, one agent invocation fitting in one Activity, HEAD-based citations, bounded fixture-scale input, and pricing that may change. [A&R]

## 9. Inconsistencies or gaps between documents

1. **No cost budget field.** CLAUDE rule 5 and ADR-010 require cost limits to be enforced, but `ReviewBudget` has only token, delegation, tool-call and elapsed fields. No `maxEstimatedCostUsd` exists, and the sample's `estimatedCostUsd` is null. [CLAUDE], [ADR-010], [CONTRACTS]
2. **Elapsed budget vs no wall-clock in the Workflow.** Workflow code may not read the wall clock, yet `maximumElapsedSeconds` must be enforced there. No document says how (Workflow time APIs or timers). [ARCH], [CONTRACTS]
3. **Tool names differ between the port and the agent tools.** `findRelatedTests` vs `listRelatedTests`, `readBuildMetadata` vs `getBuildMetadata`, and `searchCode(pattern, limit)` vs `searchCode(query)`. [CONTRACTS]
4. **Single-agent baseline vs FEATURE-006.** FEATURE-006 is an "end-to-end Correctness review". The baseline needs a SINGLE role (`reviewSingle`) covering every category. No feature explicitly owns `reviewSingle` or SINGLE_AGENT mode wiring. [PLAN], [CONTRACTS], [ADR-007]
5. **Loop pseudocode ignores the mode and the SINGLE role.** The switch has no SINGLE case and doesn't say how SINGLE_AGENT mode bypasses the planner. It also leaves open whether the planner may pick SINGLE (the enum allows it). [ARCH], [CONTRACTS]
6. **Reason field names differ.** `reasons[]` [ARCH lifecycle], `completionReasons` [CONTRACTS ReviewRunResult] and `limitations` [CONTRACTS JSON].
7. **Rejected candidates have no slot in the report schema.** The docs require tracking rejected candidates separately from unverified ones, but the JSON only has `unverifiedCandidates`. The `NEEDS_REVIEW` semantics and the mapping from status to report section are undefined. [ADR-006], [CONTRACTS]
8. **Status terminology.** The architecture says "not report `VERIFIED`", but the enum value is `SOURCE_VERIFIED`. [ARCH failure table], [CONTRACTS]
9. **The manifest is missing from ReportReference.** EVAL requires report.json, report.md and a manifest, but `ReportReference` holds only the JSON and Markdown paths and one sha256 (which file's hash is unclear). [EVAL], [CONTRACTS]
10. **Dependency table vs diagram.** FEATURE-011 is listed with deps 005 and 010, but the diagram shows only 010. FEATURE-012 is listed with 003, 010 and 011, but the diagram shows only 011. FEATURE-014 is listed with 011, 012 and 013, but the diagram omits 011. [PLAN]
11. **No test repo before FEATURE-013.** FEATURE-004, 005 and 006 need a synthetic repo, but the seeded fixture comes later (FEATURE-013). [PLAN]
12. **Goldset placement.** `samples/goldset.json` sits next to the fixture. If the fixture is the allowlisted repo or lives in the same Git tree, tool exclusion must be enforced. No exclusion mechanism is specified. [EVAL]
13. **SUBMITTED state without a DB.** It's unclear where SUBMITTED lives before the Workflow starts, given that there's no app DB. ReviewProgress, PlannerInput, ReportInput, ChangedFile, DiffExcerpt and the other types are referenced but never defined. [ARCH], [CONTRACTS]
14. **Limits named without numbers.** Only readFile's 200 lines is concrete. Max changed files, retry counts, timeouts, default budget values and the repair-attempt count beyond "one" are left unspecified. [ARCH], [CONTRACTS], [EVAL]
15. **Idempotent conflict semantics are undefined.** It isn't said what happens on the same reviewId with a different payload. [CONTRACTS REST]
16. **Model name needs verification.** `deepseek-flash` / "DeepSeek Flash" is assumed. ADR-002 itself requires proving it. [README], [ADR-002]
17. **No approval path.** "Explicitly approved" code transmission is allowed, but no approval mechanism or recorded decision is defined. [A&R A-02], [CLAUDE rule 8]
18. **Precision vs recall definitions.** Recall counts "verified findings", but precision demands semantic judgement, so the two denominators are inconsistently defined. [EVAL]
19. **AGENTS.md** is referenced by the README and CLAUDE.md (as Codex instructions) but was not among the inputs. It may contain rules that diverge from CLAUDE.md. [README]
